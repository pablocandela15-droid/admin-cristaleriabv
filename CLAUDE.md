# Reglas para Claude en este repo (panel de Cristalería BV)

Panel de administración de Cristalería Baix Vinalopó (Cristalería BV): Admin Panel, Super Admin y login, hechos a partir del panel de referencia de OficiosOsIA (sin nada de restaurante). Proceso completo y guía práctica: [docs/PROCESO-DE-CAMBIOS.md](docs/PROCESO-DE-CAMBIOS.md). Puesta en marcha de un entorno: [docs/DESPLIEGUE.md](docs/DESPLIEGUE.md). Obligatorio:

- **Ramas.** Cada cambio en su rama `feature/<tema>` o `fix/<tema>` (desde `staging`), con PR a `staging`; fusiónalo hacia `staging` con merge commit para verlo en la demo. **Nunca** hagas push a `main`, nunca fusiones un PR hacia `main`, nunca `push --force`. Producción solo cambia cuando el dueño acepta en GitHub un PR `release/X.Y.Z → main`.
- **Vercel a mano, nunca.** No despliegues ni promociones nada con la CLI o la API de Vercel (`vercel --prod`, `vercel deploy`, `vercel promote`, `create_deployment`, `request_promote`, `request_rollback`…): se saltan el control de publicación. La única excepción es volver atrás cuando el dueño lo pida expresamente, y entonces con *Promote* sobre un despliegue de producción anterior hecho desde git.
- **Releases.** Solo con lo que pida el dueño: `node scripts/release.mjs pendientes`, luego `preparar '#PR' <sha> … --objetivo "…"` (primero con `--simular`), `git push -u origin release/X.Y.Z` y PR a `main` con la descripción de `node scripts/release.mjs informe --head release/X.Y.Z`. Si se bloquea por dependencias o conflictos, explícaselo al dueño: **no** añadas cambios ni uses `--no-depende` sin su «sí».
- **Commits:** `git -c user.name=Claude -c user.email=noreply@anthropic.com commit …`. Tipo convencional (`feat(…)`, `fix(…)`…) y, si cambia un comportamiento, líneas `Antes: …` / `Ahora: …` en el cuerpo. Para `preparar`, exporta `RELEASE_GIT_NAME=Claude RELEASE_GIT_EMAIL=noreply@anthropic.com`.
- **Antes de subir a staging:** `npm run test:cambios` + `npx tsc --noEmit -p tsconfig.app.json` en verde (solo los tests afectados por lo cambiado; si tocas `supabase/migrations`, lanza también `npm run test:nucleo:db`). **La suite completa** (`npm test`, `npm run test:nucleo:db`, `npm run build`) **solo al preparar una release**, sobre la rama `release/X.Y.Z`.
- **Supabase:** el proyecto de la demo primero (variable `SUPABASE_REF_DEMO`). Producción (`SUPABASE_REF_PRODUCCION`) **solo** después de que el dueño acepte el PR de la release y lo pida explícitamente. Migraciones en `supabase/migrations/`, con su vuelta atrás en `supabase/rollbacks/`.
- **Después de subir:** a `staging`, comprueba que Vercel publica la demo (READY) y dile al dueño qué probar; a `release/X.Y.Z`, que la preview de la candidata está READY y sirve esa versión (`node scripts/comprobar-despliegue.mjs <url> --version X.Y.Z --commit <sha>`), y dale la URL del PR y de la preview.
- **Versión:** `X.Y.Z` en `versionado.json` y entrada en `CHANGELOG.md`; los escribe solo `scripts/release.mjs`. No los edites a mano.
- **Nombre del negocio:** en `src/config/negocio.ts` (y en `index.html` y `public/manifest.webmanifest`).
